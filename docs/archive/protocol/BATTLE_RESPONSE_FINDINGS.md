## Response contract

All four successful response consumers run only after `ChangeReturnValue` maps the response code to `PROC_CODE.OK` (`ComManager.cs:2269-2311`). `session_id` replaces the current session, so it should remain usable as `RTDSESSID` (`2247-2252`). Code parsing takes the first 16 response characters and splits the first comma/colon (`2284-2301`): keep `code` first in compact JSON. DTO membership alone does not prove every field is required, but consumed fields must retain meaningful values.

## Helper and second tutorial / ordinary quest entry

`GameManager.cs:13-15` defines Tutorial1=10000 and Tutorial2=10001. Ordinary selection assigns MainMenu.m_SelectedQuest (`MMQuest.cs:446`), checks quest availability/stamina and six-member-party minimum (`499-520`), then SelectHelper (`523`; another return path `616-626`). `MMHelper.cs:99-112` fetches only when `ClientData.IsNewestHelpers()` is false; freshness is 120 seconds (`ClientData.cs:3045-3055`). Explicit refresh invokes get_helpers at `MMHelper.cs:255`. Client displays helpers in response order (`70-86`), and selected row becomes MainMenu.m_HelperData (`190`). Empty/null list sets helper null and proceeds to confirmation (`120-150`, `289-292`); six-member quests use their dedicated confirmation.

Standard confirmation selects the quest and bonus flags, fetches its level master (`MMQuestConfirm.cs:440-468`), creates party/map (`472-478`), submits FormUnits (`513`), clears hierarchy/result accumulation and enemy info, then enters MAIN_GAME (`526-530`). `GameManager.SaveFunck` subsequently sends order_quest for all quests except Tutorial1 (`389-409`), including Tutorial2 when MainMenu.m_HelperData is non-null. Thus Tutorial2 shares this network path and real-hash request branch (`ComManager.cs:1281-1297`), while retaining tutorial battle UI (`GameManager.cs:342-345`). There is no Tutorial2/10001 special selection/helper path in the searched `MMQuest.cs`, `MainMenu.cs`, `MMHelper.cs`, `MMQuestConfirm.cs`; exact content gating/availability still depends on master data and is not proven by this path trace. Important static edge: empty helpers can reach confirmation with null helper, but SaveFunck's fresh order is guarded by helper != null; do not assume empty helper lists produce a valid fresh ordinary battle.

## Title restore / decline

First-tutorial path queries get_quest_info (`TitleMenu.cs:981`); on OK status !=1 it fetches level and orders the tutorial (`992-1008`), while status 1 loads local last enemy info (`1000`). It constructs the fixed FIRST_FRIEND helper, resets hierarchy and enters MAIN_GAME (`1015-1027`).

Ordinary restore path AuthorizeUser → get_quest_info (`1030-1044`), requires OK and IsBattle (`1047-1063`), then shows BATTLE_RETURN (`1066-1068`). Accept sets local m_DropNone=true (`1071-1075`). Decline goes to mode 3010 (`1077-1080`), which calls SaveFuncGameRestoreClear and chooses tutorial/gacha/main menu (`1167-1182`); no explicit quest-abandon request occurs in these branches.

Accept additionally requires local `m_ContinueCt == ComManager.m_ContinueCount` (`1084`); otherwise it also goes to 3010. Party/helper are reconstructed from local save (`1094-1144`), quest comes from local m_QuestID (`1150`), player snapshot is restored while preserving current total/paid/free point balances (`1151-1159`), and enemy info comes from server (`1161`). No quest_id equality check against ServerBattleInfo appears in this shown title branch. SaveDataManager saves quest ID/continue count (`1056-1057`) and hierarchy (`1335`), restores hierarchy (`1392`).

Upon battle start SaveFunck sends no new order when restored selected quest matches local quest and server status is 1 (`GameManager.cs:411-430`). A changed selected quest or non-battle status clears local restore and orders with `resume_id=old local quest ID` (`417-428`). This establishes the client input meaning, not server resume authorization or reward semantics.

## Failure, retire, and continue

Game over opens the continue dialog (`GameStatus.cs:62-70`). ContinueYes sends only when local total_paid_point >=1 (`118-133`), using `PlayerData.ContinueCount+1`. The request includes ver/retry/floor/quest_continue, no token or quest ID (`ComManager.cs:1480-1488`). The global count is temporary request state and resets to zero after the coroutine (`1465-1477`); the UI increments PlayerData.ContinueCount after IsEnd (`GameStatus.cs:110-114`), then invokes BattleManager.Continue (`86-91`). IsEnd checks only m_SeqEnd, not success (`ComManager.cs:488-499`); the UI here has no separate GetReturnCode check. Error handling in the shared network coroutine must therefore be preserved rather than treating completion as an independent server success guarantee.

ContinueNo sets m_BattleWin=false and schedules fade (`GameStatus.cs:137-147`). Active retire confirmation sets the same false flag and GameStateRetire (`BattleMenuManager.cs:413-418`); GameStatus closes retire dialog and fades (`73-84`). Both reach common cleanup, SendDropData, local NowQuestResultSave, and StartTitleMenu (`GameStatus.cs:25-48`). StartTitleMenu actually changes to MAIN_MENU (`GameManager.cs:563-572`). MainMenu detects non-win and clears local restore (`MainMenu.cs:202-205`); only win selects QUEST_RESULT in the inspected dispatch (`441-453`), which invokes clear_quest2 (`MMResult.cs:246-249`). Saving an in-memory result during failure is not evidence it is submitted to clear_quest2.

SaveFuncGameRestoreClear disables local restore header (m_Enable=0) and commits preferences (`SaveDataManager.cs:914-945`); it also clears last enemy info. It does not issue a network request in that method.

## Multiple hierarchy transition

Stairs resolve the next **quest ID** from type-20 enemy drop_id and quest master (`FieldObjectManager.cs:88-111`). Accept sets next-hierarchy flag (`144-154`); transition awards/saves current layer result, switches SelectedQuest to NextQuest, creates party/map and downloads the next quest's level (`174-187`). Successful load enters MAIN_GAME with next-hierarchy flag (`190-204`). SaveFunck increments hierarchy and orders the new quest with resume_id=0 (`GameManager.cs:391-400`), then resets flag and saves restore (`437-447`). `ComManager.cs:1275-1279` sends new quest ID and the incremented floor. ClientData.QuestHierarchyClear resets floor to zero and clears result list (`4008-4019`); NowQuestResultSave appends per-quest ID and floor (`4022-4026`, `4070`). Final MMResult submits accumulated clear_quest2. Do not model all floors as the same quest ID. Download/version failure rollback handling is visible at `GameManager.cs:494-549` and is not evidence of an extra battle transaction.

## Error and retry semantics

`CommunicationRTD/COM_RESULT.cs` and `ComManager.cs:343-397`: SUCCESS=4096→OK; PAID_POINT_NOT_ENOUGH=8961→ERROR; QUEST_BAD_CONDITION=9472→its dedicated proc code; MASTER_DATA_CHANGED=8209→RESTART; AUTH_REQUIRED=8196→RETRY; DB_ERROR_DEADLOCK=12290→DB_DEADLOCK. Unknown codes retry. Missing/short/transport-error bodies retry (`2274-2289`). Non-OK bypasses response application (`2301-2308`). GameManager handles QUEST_BAD_CONDITION with DLG_QNA then server-error exit (`477-483`, `359-372`).

Shared sequence retries up to five times, regenerating request JSON each attempt (`2096-2175`); RETRY triggers reauthorization, DB_DEADLOCK retries without it. Exhaustion shows reconnect dialog and repeats outer loop (`2201-2209`); ERROR shows top/title dialog and changes to TITLE (`2181-2199`). OrderQuest creates a new GUID token once per logical call (`1248-1255`), while retry regeneration reuses m_Token (`1317`). Continue has no analogous token. A reasonable emulator design needs duplicate protection, but the original server key, retention window, balance-debit order, and floor/count validation remain unknown.
