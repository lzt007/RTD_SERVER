# 客户端中文映射与字体注入可行性

2026-10-28。本轮仅静态分析；没有编译/安装新客户端，没有操作模拟器、存档、配置或现有服务。以下是建议方案，不是已完成的汉化或性能验收。

## 结论

“中文字体资源 + 两列翻译表 + 启动时加载映射 + 显示时查表”可行。项目已有Cecil派生程序集和兼容旧Mono的辅助DLL构建链，可添加自有汉化辅助模块与必要的启动/显示钩子，不必预先假定某个现代插件框架能运行在此客户端。

推荐运行时映射为主，少量模板调用点、字体和图片资源补丁为辅。直接修改文本资源也可行，但并不能免除字体、动态模板和缓存处理。

## 四项需求的具体实现边界

### 字体注入

为旧NGUI生成兼容的位图字形数据、纹理与材质，包含所需简体字、原日文/ASCII/数字和原特殊符号；不能把中文专用字表直接替代原字体而丢掉未翻译文本。可利用UIFont.replacement，或在新标签绑定字体时选择替换字体；继承必要的字号、基线、间距、符号和shader，不强行把所有设计字体/数字字体统一成一种。

优先生成目标译文字集并保留原字形。若一张纹理放不下，多页并非该旧UIFont的现成功能：它的纹理、UV和材质路径以单页为基础，需要分字体或扩展渲染，不应只增加几张PNG就假设自动生效。

插件加载PNG并不保证纹理在GPU上仍为Alpha8；须实测get_format、CPU/GPU保留和峰值分配。可比较“兼容资源模板离线生成Alpha8字体资源”和“PNG+字形表运行时加载”两种路径后再选。现有纹理与旧shader是较稳妥的适配基础，尚未制作候选字体。

### 两列表格

主表严格保留“源文本”“中文文本”两列，中文初始为空；源文本按实际Unicode精确保留，不随意Trim或改变换行。PC可编辑XLSX，发布时导出UTF-8 CSV或JSON；启动时一次解析，不让旧Mono在显示过程中读取Excel。CSV必须正确处理引号、逗号、BOM与多行文本。

采集范围包括：GameText/TextAsset、代码ldstr常量（原版及派生补丁）、场景与prefab的显示字段、已恢复主表的名称/剧情/技能说明、Android资源和本地HTML。源路径、主表字段、GameText键、调用位置等存在独立索引中，主翻译表仍为两列。单纯扫描DLL或TextDatabase不能称“全部字符串”。

去重后同一源文本只能得到同一译文；如果存在语境歧义，需要独立上下文覆盖规则。动态玩家名、数字组合无法静态枚举全部结果，应采集模板/片段。图片中烘焙的文字不是字符串，须另做图片替换；原生Android/HTML显示也不经过UILabel。

### 启动加载

默认空字典，首次显示前尝试读取本地表；无文件、不可读或解析失败时保持空字典。先构建临时映射并验证，成功后一次发布，不能半张表已生效后解析错误退出。空中文单元格表示不替换；冲突的重复源文本应在发布校验时报错。字体资源失败时停用需要该字体的汉化、保留原文，避免全界面缺字。

加载器和模块须对客户端自带mscorlib/UnityEngine编译。现有`build-rtd-local-client.ps1:28`已有/noconfig /nostdlib与客户端引用方式可复用。外置资源放到客户端实际可读的应用目录；不依赖桌面路径，也不在每帧检测文件。

### 显示映射

主要兜底点建议为UILabel.ProcessText：从原mText取翻译并生成显示缓存，再由原换行/尺寸计算/Print流程渲染，保留mText及text getter原值。不要全局改string、序列化数据或协议字段。只改setter会遗漏序列化字段直接恢复的预置文本；只在最终顶点绘制时换文字会使测量、折行和显示不一致。

GameText.Get/GetText或具体UI调用点在格式化前翻译模板，例如`体力 {0}/{1}`再代入数值；非GameText拼接语句少量定点处理，不对所有String.Concat/Format做全局扫描替换。中文译文要校验`{0}`等占位符和NGUI颜色/符号标签。用户输入、密码和玩家自定义名称保持原内容。

初版可只支持精确匹配及已有模板入口；未匹配内容保留原文，用有界去重的遗漏采集补充。不能宣称一个UILabel钩子就自动覆盖全部动态文本和图片文本。

## 性能判断

- 字典用TryGetValue，按文本变化而非逐帧逐条扫描翻译表；哈希与文本长度有关，查找平均常数级。只返回已有译文引用，避免不必要分配。短文本上万条通常为MB级数据，具体取决于剧情长度、字典容量和缓存，尚未做此客户端实际测量。
- 大表解析和字体加载一次放在启动/加载阶段；不逐帧读CSV、不每次正则遍历全部词条、不无限缓存带计时/数值的动态句子、不为每次未命中打日志。
- 字体是主要增量风险。单页2048² Alpha8原始像素4MiB，RGBA32为16MiB；4096²分别16/64MiB，均不含mipmap、CPU副本、上传临时缓冲和字形对象。PNG文件小不代表运行内存小。
- 多材质/图集可能拆分NGUI批次；译文长度和字形度量影响换行、裁切、按钮排版。只对稳定变更的标签做重排，字体共享并一次加载，避免频繁标脏。

判断：正确实现的精确映射预计不会有很大的持续运行开销，但不能在该旧Unity/模拟器上提前承诺零影响。最小样本应测启动耗时、峰值内存、正常界面帧耗、draw calls与缺字/折行，重点观察字体加载和标签是否被错误地每帧重建。

## 直接修改文件的可行性

| 目标 | 可行方式 | 边界 |
|---|---|---|
| TextDatabase | 修改TextAsset内人类可读值并重写序列化文件 | 保留键、计数与分隔规则；不做等长字节覆盖 |
| 场景/prefab | 修改UILabel等显示字段 | 必须使用正确的旧Unity序列化结构重写，保护引用/布局 |
| C#代码常量 | Cecil修改确认用于显示的ldstr或模板 | 不翻译URL、资源名、协议键、对象标识和其他逻辑常量 |
| 下载主表 | 修改名称/说明等显示字段 | 保留ID/数值/结构，同步下发版本和缓存策略，不污染业务主数据原件 |
| 图片内文字 | 重绘并替换对应纹理/图集区域 | 字符串映射不覆盖；保护UV、尺寸与透明通道 |

文件修改仍需要中文字形。客户端可能从服务器/缓存再次取得主表，APK内改值会被覆盖；必须同步资源版本/缓存命中策略。派生APK需沿用可验证的重打包流程，最终安装版本还需处理签名；原件保持可回退。不能在未核实具体校验机制时假设“关掉一次校验就能改所有文件”。

## 建议的最小验证顺序

1. 不带译文表启动，确认字典为空且原日文界面保持。
2. 仅做少量固定标签、一个带参数的模板和一段长剧情译文，验证预置标签与动态文本。
3. 注入小字集字体，验证简体字、原日文、数字、NGUI符号、对齐与换行。
4. 记录加载峰值与帧耗、验证无逐帧重建，才扩大到完整采集表。
5. 补齐本地HTML、原生弹窗和图片文字等不经UILabel的来源。

该顺序是技术验证建议，本轮未实际执行这些改包或设备步骤。
