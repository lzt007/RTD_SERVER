# 数据完整活动关卡恢复设计

范围：恢复原始地图和关联数据完整的活动关卡，保留星期、前置通关、活动积分条件；不以编造敌人、掉落或地图填补原始缺口。不安装无关软件包。

## 方案

采用启动时内容审计生成可玩集合，并由入场、结算和后台共用。拒绝简单开放所有地图文件：已确认有缺敌人表、缺掉落以及缺楼梯目标地图的关卡。固定手写名单会在数据更新后失效，因此不作为主要方案。

## 完整性判定

验证关卡主表、地图编码及尺寸、起点、敌人表、实际地图槽位和 boss/death 的敌人主表、普通掉落及掉落角色、挑战与奖励引用、前置条件引用。对楼梯递归检查目标地图、敌人和可结算出口，不能只检查首层。

数据完整与协议支持分别记录。尚不支持的条件须先根据客户端源码核对语义，再实现；不得把未知类型当作通过。检查关卡引用的场景、模型和纹理资源是否可用，分别记录原版资源与既有替代资源。

## 服务端修改

新增活动内容审计模块，输出可接入单层关、多层关及排除原因。API 初始化加载结果；入场、clear_quest2 分流及后台可玩集合统一使用该结果，避免可入场不可结算。保留已支持剧情关与教程行为。

查明开放类型 7/9、挑战类型 22 以及活动特殊奖励的客户端语义。历史限时活动须保留原时间限制；如需重开旧活动，必须用现有本地活动排期明确覆盖，并在报告中说明。

## 验证与上线

先编写失败测试覆盖每日关入场及结算、缺表拒绝、楼梯依赖缺失拒绝、星期和前置条件、重试幂等。对所有入选关卡运行生成及结算检查，执行现有回归测试。输出逐关审计清单及不能恢复原因。

生产更新前备份被替换代码与配置，检查生产和工作区差异，不覆盖现有部署脚本修改及真实账户数据库。以独立临时数据库验证后同步代码；重启 API 前检查活动战斗和进程启动方式。资源文件只补入已确认存在的原始数据，不生成替代游戏数值。

客户端全流程最终需要实机验证；服务端测试通过不得声称所有关卡已完成客户端验收。
