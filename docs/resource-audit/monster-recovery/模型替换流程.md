# 缺失敌人模型替换流程（后续代理必读）

适用：缺失敌人模型/贴图的提取、同族复用、跨 Unity 版本兼容、绑定修正、打包及部署。修改前先读本文件和仓库 `AGENTS.md`；不能仅凭旧脚本能运行就批量替换。

## 当前确认的结果与边界

2026-11-04，用户实机确认：银色史莱姆显示正常；狼的奇特外形是设计本身，并非缺头缺腿；最终 `wolf-native-activation-v4` 模型显示正确。v3 清理无关对象后仍出现人物下方的完整狼，v4 对齐原生激活标记后用户确认模型正确。

**完成关卡时客户端闪退仍未解决。本次只完成模型替换，不是结算或资源释放修复。** 不得把显示成功、HTTP成功、离线测试通过或回退后可结算，写成通关闪退已经修复。实机确认不代表所有属性、所有关卡或全部动作均已穷尽测试。

最新跨种族/角色Boss经验与纠错见 [修复经验与纠错记录](修复经验与纠错记录.md)，当前生产状态见 [审计入口](../README.md)。以下第4节为早期狼修复复现，不是覆盖当前278包的批量部署指令。

## 1. 先确定真实加载需求和已有资源

1. 从当前有效开放范围取主线与已完成修复的活动；回查原敌人记录，保留原模型/纹理名和引用关卡。原客户端先构造敌人安排表，再枚举唯一敌人；必须覆盖全部18槽、Boss和Death，不能只查地图字节中实际出现的槽。
2. 分开核对 APK `Resources` 绑定、APK 内资源包、90个预载文件、服务器原优先目录及新增备份。不能只按文件名或某个目录未命中就判缺失。无名对象、原始序列化缓存也要解析；同内容文件按哈希记录所有来源。
3. 不得按ms前缀排除候选；普通敌人和角色型Boss都要检索旧APK、旧缓存、新APK、新缓存。角色型敌人还要追角色分组包、对应书本、动作和特效。包存在不等于资源名可导出，也不等于缓存的 URL/版本会命中。
4. 原始素材存在时必须沿用；仅替换确实缺失的外观。保留属性、类型、等级、数值、掉落、挑战、地图和开放条件。等级/属性后缀不一定对应新几何；同族复用、重着色及等级映射必须标记推测。

本次入口：`scripts/list_playable_monster_models.py`、`config/monster-recovery-models.json`。原始加载定义摘录：`../loading-chain/loader-definitions.tsv`。需要重建资源目录时运行 `../loading-chain/catalog.py`；它生成本地 `catalog.json`，供动作与 APK 外部指针解析使用。大型生成目录及原始二进制不包含在模型提交中，需在具有原输入的环境重建。

## 2. 按实际客户端链核对加载、克隆和控制范围

以实际分发程序集为准，记录哈希、方法和证据；源码或旧版反编译仅作对照。本次关键路径：

`LoadEnemyAssetBundle → EnemyManager.ResourceLoad/AddEnemy → AssetBundle.Load(ast_<模型>) → Instantiate → 挂父节点/Enemy/Billboard → Enemy.Init → SetEnemyParameter`

以上是普通模型式敌人分支。角色型由原IsUnitEnemy类型22/24/30/31/33/37判定：ChangeUnitEnemy在gid>0时从数字分组包Load原模型名，gid=0时从独立包Load ast_原模型名；地图另有按symbol选择的书本。根Animation供el_boss_tob/六人版入战动作使用，原方法自己镜像X并设Z=.01，不能强选Y180副本。动作须追原type/MotionAssign；Orlgadia使用org待机/攻击，不是ms03_sen猜名。

核对预制体导出名、按类型加载的对象、纹理名以及原动作曲线路径。`Enemy.Init`取实例子级主渲染器；淡出/颜色控制遍历实例子级。**载入的原型与实例化的敌人不是同一个对象；不属于实例子树的场景对象不会自动接受相同生命周期管理。**

遇到影像残留，先区分：贴图被串用、正常实例未销毁、载入原型意外显示、无关源场景副本被预加载。不能直接认定“图集污染”，更不能删除正常狼面片、改变怪物设计来掩盖额外显示。

## 3. 跨版本转换必须检查的内容

| 检查项 | 本次经验与要求 |
|---|---|
| 序列化 | 目标为原客户端 Unity 3.5、serialized format 9。不能只改版本字符串，必须按目标 type tree 写入并重新解析。 |
| Shader/材质 | 新版 shader 不直接塞给旧引擎；使用审计过的旧 Android shader 及匹配材质结构。保持渲染状态，检查透明区、颜色、UV和实例材质赋值。 |
| 网格 | 核对顶点布局/stride、子网格、索引范围、实际解码的非退化面片及绕序，不只检查声明的 triangleCount。原生存在 topology=0，不能宣称旧版一律不支持三角列表。 |
| 蒙皮/动作 | 检查四权重归一、骨索引、bindpose、每个渲染器所属骨架及原动作路径；用静止/待机/攻击采样对照源数据。renderer-local 与世界/骨架坐标要明确。原源已有的局部位移不等于转换损坏。 |
| 压缩数据 | 修改非压缩几何时核对 CompressedMesh，避免残留另一份权威几何。 |
| 纹理 | 核对旧 RGBA4444 位序、RGBA32、垂直方向、alpha、尺寸和mip字段，写回后逐像素对比。灰银重着色必须标为推测，不冒充原银图稿。 |
| 内部身份 | 每种输出、每次不兼容修订使用独立内部 serialized/CAB 名；PPtr的FileID/PathID必须能闭合，不能依靠数值碰巧相同。 |
| 对象归属 | 从每个导出对象递归求引用闭包，仅保留所有导出的闭包并集和 AssetBundle 元数据；每项 preloadIndex/preloadSize只指向其依赖。不能把整个源文件的对象挂到每张贴图的预加载表。 |
| 原型状态 | 对齐审计过的同版本工作包，包含子节点激活标记。Unity 5 源场景的标记不能直接当作 Unity 3.5 资产的约定。**本次旧包GameObject标记为0，新源为1；v4对齐为0。不能将此值盲目推广到其他Unity版本。** |

v2 每个狼包还带有不属于任何导出的52个源场景对象（25个GameObject、25个Transform、一个Animation、一个SkinnedMeshRenderer）。v3移除它们、逐导出重建预加载表，改善碎块，但未阻止正式原型自身显示；v4再对齐剩余26个GameObject的激活标记。**“有两个渲染器”不是必须保留两套场景副本的依据，必须先看归属。**

不要凭“狼不像狼”判几何损坏。此次外形经过用户确认；错误的最初解释应保留更正，不应继续传播“缺头缺腿已修复”的结论。

## 4. 本次可复现构建顺序

所有命令从仓库根执行。使用独立 Python 环境安装 `requirements-model-recovery.txt`；运行服务不需要 UnityPy/numpy。输入 APK、预载、原金史莱姆和备份狼必须就位；路径及SHA见 `config/monster-recovery.json`，原件不得覆盖。此处为早期狼批次的输入说明；后续经用户授权已把新7.0.1.0 APK纳入四来源审计，不得继续用此旧说明排除新APK素材。

先保存当前清单/输出到独立本地目录。以下构建阶段会写工作区清单，**不直接操作生产目录**：

```sh
RTD_EVENT_RECONSTRUCTION=1 RTD_SHINGETSU_RECONSTRUCTION=1 \
  python3 scripts/list_playable_monster_models.py --output config/monster-recovery-models.json
python scripts/prepare_monster_recovery.py --active-models config/monster-recovery-models.json
python scripts/prepare_wolf_strip_candidate.py --output resources/reconstructed/wolf-strip-v2-candidate
python scripts/prepare_wolf_closed_bundle.py
python scripts/prepare_wolf_native_activation.py
```

这里的 `python` 必须是安装离线依赖的解释器。没有本地目录索引时，先用同一解释器运行 `docs/resource-audit/loading-chain/catalog.py`。构建阶段名v2/v3仅表示历史管线步骤，**不能只运行第一步或把中间包当成最终可发布包**。

最终将 `resources/reconstructed/wolf-native-activation-v4-candidate/validation.json` 中八项合并到构建清单（按model匹配，先核对source/textures一致，保留推测reason），将对应八个包复制到本地最终 `resources/reconstructed/monsters/bundles/`，同时更新 `config/monster-recovery.json` 和输出 `manifest.json`。十个史莱姆包保持既有验证字节。最终清单必须标明 `wolf_revision=wolf-native-activation-v4` 并使用最终SHA/CAB名；不能只复制文件不更新白名单哈希。

可用 `validate_wolf_cpu_skin.py` 做原待机/攻击曲线的离线纹理蒙皮检查，`compare_wolf_rest_bindings.py` 对照原源与原生模板，`report_monster_recovery.py` 生成预览。预览是软件绘制，不是实机证据。

## 5. 验证及验收要分开记录

```sh
# 使用包含 UnityPy 的解释器；最终目录应有八个狼包。
python -m unittest tests.test_monster_conversion tests.test_wolf_export_closure
python3 -m unittest tests.test_monster_recovery
```

新增缺陷回归必须先对坏包/旧实现观察到失败，再对修正包通过。本次覆盖：逐导出闭包、无额外渲染树、旧格式激活标记、转换器格式/引用/动作/像素、HTTP开关与原文件优先、有效主表只改缺失外观。测试依赖本地原件和生成包，缺输入的跳过或失败不能算通过；不应为通过测试改原游戏配置。

部署前后比较**有效配置**：地图、所有非外观主表、敌人非外观字段、开放条件和运营配置；不能仅比较磁盘原文件。检查既有原优先目录包哈希、所有最终下载路径的实际响应哈希、两服务开关和健康状态。仅部署明确列出的文件；备份文件及数据库一致性副本，不用旧数据库回滚玩家进度。API初始化可能超过十秒，应等待就绪，不能因短超时误判资源失败。

客户端按包定义的固定版本缓存。替换同路径文件、更新服务器SHA或改内部CAB名，均不等于客户端会重新下载。复测前执行“取得最新数据”并重启，再新进入关卡；缓存与下载问题单独验证。

实机验收至少包含：首次遇敌、正常战斗实例、角色下方/周围无额外原型、视角与移动、属性配色、待机/攻击、受击、死亡淡出、连续遇敌、退出重进。11012「暴赫龙吼」用于本次火狼Lv1/Lv2和银史莱姆；11010「尖炎断崖」补测普通高等级史莱姆。记录具体关卡、包修订及用户反馈，不扩大确认范围。

**模型显示、加载完整性、资源释放、通关结算是不同验收项。通关仍闪退时必须明确写未解决，不能把本次模型提交当作结算修复。** 后续排查释放应沿实际实例和AssetBundle引用追踪，不以“替换前名字可能不存在”直接认定空指针，也不在没有定位时同时改Unload语义、动画、结算和外观。

## 6. 当前等级替代与批次口径

仅缺失等级的手动缩放使用Lv2=1.3、Lv3=1.6、Lv4=1.9，原模型大小保持。旧输出先去旧倍率再算新倍率，不能累乘。影型降饱和/明度并保留alpha。精确原素材优先，不能因为已有临时替代就跳过新素材。生产278包、本地287包（含9个额外辅助资源），窄范围同步并分别记数。详见经验记录与等级缩放报告。
