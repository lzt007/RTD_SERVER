# 狼游离贴图片段与资源释放排查

2026-11-04。用户实机更正：狼的奇特外形是原设计，模型修复成功。当前问题是首次遇狼后出现跟随人物的贴图片段，以及通关仍退出桌面。不再以缺头、缺腿或改变狼外形作为排查目标。

## 先处理资源包的对象归属

对当前分发中文版程序集以及当前 v2 狼包进行比对：

- `Enemy.Init`（token 0x0781，IL_0017–0021）只从实例化预制体下取得主 SkinnedMeshRenderer；`Enemy.UpdateColor`（0x078a）遍历该预制体子级，控制颜色、淡出和 enabled。位于另一个根节点下的渲染器不受这些操作控制。
- v2 普通狼包共117个对象。`ast_ms01_wolf_lv1` 的完整引用闭包为61个对象，其中只有渲染器113；渲染器114属于另一个独立根 `330_ms01_wolf_lv1_f_01`，其25个 GameObject、25个 Transform、Animation 和渲染器共52个对象均不属于正式狼预制体，也不被任何其他导出资源需要。
- v2 的每个导出项（包括单张属性贴图）都预加载全部116个非 AssetBundle 对象，把这套独立场景副本也带入加载范围。独立根 `m_IsActive=1`。原生旧版熊、金史莱姆也保留独立场景副本，但其根 `m_IsActive=0`，且导出预加载表按各自依赖切分。
- 之前仅比较“新狼和旧熊都有两个渲染器”，没有核对它们是否处于同一个预制体，因而漏掉了对象归属和激活状态的差别。不能把独立源场景副本误认成正式模型必须保留的第二个可见部分。

以上是静态资源和实际 IL 中可复核的事实。独立激活副本被预加载、却不受正常狼的移动/淡出/销毁路径控制，可以解释世界坐标中的游离贴图片段随视角或人物移动而变化；没有设备画面与对象实例跟踪，尚不能证明用户看到的每片碎块都来自该副本。

## 图集污染的核对范围

已检查 `Enemy.SetEnemyParameter`（0x0783）：从对应敌人包按纹理名加载 Texture2D，然后经 `Renderer.material.mainTexture` 赋给实例材质。该路径没有修改 UIAtlas 或全局纹理的操作。狼包没有 UIAtlas/字体/UI脚本对象，包内 PPtr 都是当前独立 CAB 的内部引用；v2 的八个 CAB 身份也各不相同。因此，现有证据优先指向多余场景对象的加载，而非已证明的全局图集覆盖。不能据此排除 native GPU/驱动或未观测路径的问题。

## v3 单项修正与验证

`scripts/prepare_wolf_closed_bundle.py` 从 v2 生成 v3：仅保留所有导出资源的引用闭包，删除每包52个无导出归属的场景对象，并逐导出项重建预加载依赖。每包另用独立 v3 内部 CAB 名。普通狼保留65个对象，四种特殊狼各保留62个对象；正式狼预制体、网格、UV、蒙皮、动作、材质、贴图的原始对象字节全部与 v2 相同。不改模型外形、主表或客户端结算逻辑。

`tests/test_wolf_export_closure.py` 在部署前 v2 上失败8个子项，原因均是预加载包含不属于导出项的对象；对 v3 八包通过。构建器还逐个回读，核对所有保留的非 AssetBundle 对象原始字节一致、导出名称不变。原有格式转换回归一并运行。此项验证证明对象归属和依赖被修正，不等于已观测到 Android 上碎块消失。

## 随后核对“按旧名字释放不存在资源”的假说

当前实际 IL 不支持这一路径作为已证原因：

- `GameManager.ClearAssetBundleData`（0x0a5c）遍历实际加载的 AssetBundle 引用列表，并在 IL_0023–002e 通过 Unity Object 空值比较后才调用 `Unload(true)`（IL_0086）。它不会重新按未替换前的怪物资源名查找再释放。
- `AnimationController.UnLoad`（0x0759）先按名称 `GetClip`，在 IL_000e–0014 判断 clip 非空才 `RemoveClip`；不存在某个动作名称会被跳过。
- `Enemy.UnLoad`（0x0799）清理当前实例的动画和主材质；根动画 clip 在 IL_0091–009c 先做非空判断，`GetClip` 不存在时走警告路径，不调用该分支的 RemoveClip；主 mesh 在 IL_0112–011d 也有非空判断。
- `Enemy.OnDestroy`（0x0780）仅释放攻击逻辑，不会再次调用 Enemy.UnLoad。死亡淡出后的 `EnemyManager.LateUpdate` 在调用 UnLoad 后销毁当前实例并移出列表。

这些防护并不能证明 native 资源释放安全。特别是 `Unload(true)` 会销毁实际已加载的对象，而旧流程在卸载后才切结算场景；意外激活的游离场景对象可能增加仍存在的渲染引用。v3 首先消除这项已发现的归属错误，不同时改成 Unload(false)、吞异常或泛化跳过销毁，以便实机结果能区分变量。仍须观察：碎块是否消失，以及相同资源下通关是否仍崩。若仍崩，沿已制作的79处阶段标记定位具体释放/切场景落点，不能仅凭静态分析断言空指针位置。

诊断工具与更完整结算顺序见 [结算闪退分析](结算闪退分析.md)。当前没有新增结算修复，也没有把 v3 部署或静态回归当作闪退已解决。

## 部署状态

v3已定向部署正式环境。18个资源下载哈希通过，所有有效主表、关卡、地图及运营配置与v2逐项一致；八个狼包已更换，十个史莱姆包及92个原优先目录包保留。APK与结算代码未修改。测试前需“取得最新数据”并重启，确保未使用v2缓存。

## 实机反馈后的 v4 原型状态对照

用户反馈 v3 有改善，但仍有一只完整狼位于人物下方并随人物移动。这不支持“v3已完全消除额外显示”的说法；上一轮仅清除无导出归属对象，正式预制体本身仍有一项与原生包不同的状态。

实际 `EnemyManager.AddEnemy`（0x07f4）先 `AssetBundle.Load(ast_..., GameObject)`（IL_00b3）取得源对象，然后 `Instantiate`（IL_00da）创建战斗实例；只对克隆返回值设置 EnemyManager 父节点（IL_012b）、挂 Enemy/Billboard 和执行 Init（IL_0140）。加载得到的原型没有这些实例生命周期操作。`ResourceLoad` 同样保留原型引用。该顺序为“原型自身意外显示，加上正常克隆，形成额外狼”的假说提供依据，尚非实机对象跟踪证明。

原生旧版熊、金史莱姆全部 GameObject 的 `m_IsActive` 序列化值为0，已确认显示正常的银史莱姆沿用该格式；从 Unity 5 源继承的 v3 狼26个 GameObject 全为1。v3删除无关副本并未改变正式预制体这项差异。不能只隐藏战斗实例或删掉正式渲染器，否则会破坏已正常的狼。

v4 由 `scripts/prepare_wolf_native_activation.py` 单独生成，将八包各26个 GameObject 的旧格式标记对齐为0，不改其他 GameObject 字段；所有非 GameObject 对象原始字节与v3一致，包括 AssetBundle 逐导出闭包表、mesh、动作、材质和贴图。每包使用独立v4 CAB名称。此变更是依据原生工作资源的格式对照，不将该数值简单当作现代 Unity activeSelf 的运行结果，也不能凭离线解析保证克隆激活行为。

新增格式回归在v3上八个子项失败，v4重跑时同时验证依赖闭包和旧转换器回归。实机必须同时确认：正常狼仍能显示和战斗；人物下方的额外狼消失。若狼整体不显示，或额外狼仍存在，需要定位实际运行对象/激活流程，不能将模型消失误认作修复。此轮不调整结算释放顺序。

v4已定向部署，18条下载哈希与服务检查通过，所有有效游戏配置保持不变。源转换器同时增加旧标记对齐以防重建回退；仍待实机确认正常狼保留和额外狼消失，未修改结算流程。

最终复跑：依赖闭包、原生激活标记、实际转换器共3项资源工具测试通过；转换器新增标记断言已先在旧实现上复现失败。此为离线结果，不代表已观察到Android原型隐藏或通关成功。
