# 当前中文版 Android 通关闪退静态分析

日期：2026-11-04。对象为当前分发 APK 提取的程序集，SHA-256 `c2da3b5f4d9f2d04e4987442a9cd384c8dbb23fd216fb514b58c1dcaedc6add1`。使用 Mono.Cecil 读取实际 IL；未改 APK、生产资源或狼转换器。完整转储含私有端点，故仅保存在临时目录，不纳入报告。

## 结论与证据边界

目前没有证据支持“替换模型触发服务端模型一致性校验”。已检查的请求构造读取关卡、奖励、掉落和队伍实例资料，没有读取模型文件、Mesh、材质或模型哈希。服务器记录显示 11012 的 order_quest 成功，而随后没有 clear_quest2；这使请求之前的本地路径成为首要调查范围，但不能单凭服务器未收请求断定具体崩溃指令，也不能排除网络未送达。

关键发现是：敌人资源的 `Unload(true)` 发生在切换结算场景之前，而 `QuestClear2` 在结算界面 Update 中才启动。因此，“通关时直接桌面且服务器没有结算请求”完全可能发生于资源卸载/场景切换，而不是服务器拒绝模型。是否确为该路径，需要设备日志和 native tombstone，现阶段只是有代码依据的候选。

## 实际执行顺序

1. `BattleManager::QuestClearEvent`（token 0x055e）：IL_003b 设置恢复档 ClearFlg；IL_0041 调 `SaveFuncGameRestore(false)`；随后队伍胜利动作、gameclear 动画及粒子效果。回调 token 0x05b1 在约一秒后 IL_002d 打开 Tips，IL_0039 切状态 10。
2. 离场过程中 `GameManager` 的 `SaveFunck` 协程（MoveNext token 0x0a75）可执行恢复档处理、OrderQuest 及等待通信；它不是发送 QuestClear2 的方法，不能根据名称把它当作结算提交。其末尾 IL_0713 清恢复档，IL_0728 调 `ClearAssetBundleData`，IL_072e 切场景索引 4。
3. `ClearAssetBundleData`（token 0x0a5c）遍历敌人 AssetBundle：IL_0085 压入 true，IL_0086 `AssetBundle.Unload(bool)`；然后清列表，IL_00d2 `Resources.UnloadUnusedAssets()`，最后 IL_00f0 `UnloadAsset_PlayerUnit(true)`。这里同时涉及敌人与玩家资源，不能只盯狼。
4. `MMResult::Update`（token 0x0c24）先选择 `m_NowResultData`，IL_033a 调 `Init`；随后 IL_035e `SetupNewUnitFlag`，IL_0364 `SetupClientData`，IL_036f 才调用 `ComManager::QuestClear2()` 并启动协程。`MMResult::Init`（0x0c29）本身先读取玩家/结果资料并初始化面板；这些本地步骤也早于请求。
5. `ComManager::CreateRequest_QuestClear2`（token 0x0e3a）构造请求；例如 IL_009d exp、IL_00b3 game_money、IL_00c9 quest_id、IL_0105 yorisiro_exp，之后掉落 units、挑战 ID 和队伍实例资料。此处没有发现资源内容校验。请求协程 MoveNext token 0x0f2d 在 IL_0057 绑定该构造方法。

## 自定义补丁及替换模型

实际 `GameManager::Update` 首部含 `RTDFlow.Tick`。源码 Tick 有托管异常捕获，并会反射读取游戏/UI 状态；这不能保护 Unity native 崩溃，也不能仅凭存在补丁就认定补丁导致闪退。已对分发程序集内的 RTDFlow 进行补充核验，见下文；尚未进行隔离诊断包实机比较。

11012 本次变更覆盖狼 10200/10210 和银 slime 12100；银 slime 正常显示仅证明已成功加载/渲染，不能证明销毁、异步资源回收安全。正式狼撤下只是隔离变量，不是修复结论。

20710 本次有效敌人 10303/31030/41028/41033 未变化，不能把该关通关崩归因于此次狼替换。其玩家型敌人 i01_wz_stk_dark_01 会加载重建书资源，共同 Mesh 格式或生命周期问题值得检查，但尚无 native 证据。旧文档 `docs/protocol/2026-11-03-book-crash-investigation.md` 描述的是“进入关卡崩”，旧 v1 book triangle-list 已由 v2strip 修正；不能将旧问题直接当成此次“通关崩”的根因。

## 补充核验：实际补丁、原版对照与实例生命周期

已从当前 APK 单独提取 `RTDFlow.dll`，SHA-256 `bbca76f7c270a8ba75c0ebedb959b8df6a739807128db7dfabc2d6d27cbd5ba4`，与本地 build/RTDFlow.dll 字节一致。实际 Tick token 0x000d，IL_0017 读 loadedLevel，IL_001c 比较场景 4，不等则 IL_001f 退出；场景4时才查找 TutorialDialog 等状态。实际 IL 含 RTD_FLOW_ERROR 异常记录。因卸载发生在切到场景4之前，战斗场景中 GameManager 注入 Tick 会提前退出；不能把源码的整个 Tick 状态采集逻辑误认为在战斗卸载前均执行。此结论以场景索引仍非4为前提；诊断日志应记录 loadedLevel 确认。

与 `RTD_CLIENT/build/original-managed/Assembly-CSharp.dll` 逐方法比较指令文本（包含偏移及操作数）：`ClearAssetBundleData`、`QuestClearEvent`、`SaveFuncGameRestore` 三者完全一致。因而敌人 Unload(true) 并非此次中文补丁新引入。原版流程相同并不能证明重建资源与其兼容。

恢复档保存 token 0x10c1 已完整扫描：前部按游戏状态、教程关、下一层标志决定是否跳过；保存玩家/关卡/面板/战斗/敌人生命、位置、回合等快照，末尾 IL_1202/120e JSON 序列化，IL_1222/122e 保存字符串，IL_1233 CommitPrefs。其直接调用中没有模型内容或哈希校验、没有结算网络调用。其读取 BattleManager.Enemy 等 Unity 对象，故仍存在对象状态/序列化异常候选；“无模型校验”不等于“此方法不可能出错”。

不能证明卸载时“所有 LoadEnemy 实例尚在场景”：`EnemyManager::LateUpdate`（0x07ed）对 CanRelease 为真的实例先 `Enemy::UnLoad`（IL_0029），再 Destroy(gameObject)（IL_003f）并移除列表。`Enemy::CanRelease`（0x0796）要求 RefCount<=0 且 fadeTime<=0；`RemoveEnemy`（0x07f8）只递减引用计数。因此此前死亡且淡出完成的敌人可能早已释放，存活/仍引用的实例则可能留在场景。`ClearAssetBundleData` 本身没有先遍历并销毁所有敌人实例，也没有等待全部销毁完成的屏障；它直接卸载包后才切场景。静态 IL 证明这些调用的先后关系，不能证明某次复现时列表数量、GPU引用或原生对象状态。

诊断包应在 Unload(true) 前后记录 enemyList.Count、每个敌人的 RefCount/fadeTime、Unity instance ID 与资源名，以及 loadedLevel；日志只包含上述非敏感信息。若崩在敌人淡出阶段，另在 Enemy.UnLoad/AnimationController.UnLoad 前后加标记；若崩在包卸载阶段，再单独验证延迟/Unload(false)。不应同时改动 Tick、动画释放和包卸载，否则无法判断有效变量。上述补丁仅是定向计划，尚未制作或部署。

可证：实际保存/胜利/包卸载方法与本地原版一致；保存与所检查请求构造无显式模型哈希读取；包卸载在结果请求之前；敌人存在提前释放路径。不可证：所有敌人均仍存在、实际崩在卸载、模型替换必然为因、服务器所有路径均无校验、Android16本身为因。尚需实机栈与阶段日志。
