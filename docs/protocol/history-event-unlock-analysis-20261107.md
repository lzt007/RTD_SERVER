# 历史活动积分解锁：完整分析结果

- 事件：2026-11-06 晚至 2026-11-07 凌晨，验证完成于 2026-11-07；时间统一为 Asia/Shanghai。
- 目标：「歴史の闇を知りし者／知晓历史黑暗之人」20710、20711、20712。
- 源码基线：服务端 `346d856`，客户端 `c6150b3`；已有计分修复来自服务端 `2fd7d0b`。
- 本文是本次调查的完整结论；操作步骤见 [修复方法与回放手册](history-event-unlock-fix-20261107.md)，入口见 [事件索引](history-event-unlock-20261107.md)。

## 1. 结论及根因

实际部署没有完整应用仓库中已有的积分修复：首次检查时缺少 `event_point_recovery.py`，敌人生成函数没有接收原活动 ID，单层及多层入口也没有传入该 ID。生产运行配置 revision 40 已开放三关，未配置显式积分覆盖；缺失积分一直按 0 返回。

这造成了确定的失败链：服务端下发目标杂兵每只 0 分 → 原客户端正常击杀仍累计 0 分 → 正常通关无法取得该活动积分 → 5 分、50 分关卡继续锁定。资源包外观或激活标记变化不能补上这条协议缺口。

部署最小四文件修复后，目标杂兵每只恢复为 1 分，其他敌人保持 0。安卓模拟器正常通关 20710 上报 7 分，服务端返回 4096、余额持久化为 7；完全重启应用并重新登录后，20711 解锁，20712 因不足 50 分继续锁定。没有修改客户端游戏逻辑、原始门槛或历史玩家积分。

## 2. 原始关卡条件

原始 `QUEST_MASTER` 的条件如下，不能按常见游戏经验擅自增加逐关前置：

|关卡|原名|产出活动 ID|解锁活动 ID|累计门槛|原通关前置|
|---|---|---:|---:|---:|---|
|20710|召喚|100001|100001|0|10000|
|20711|降臨|100001|100001|5|10000|
|20712|それでも私は…|100001|100001|50|10000|

原主表还含历史日期条件；本地运营日程替代过期日程，不应覆盖积分或教程条件。积分累计且不消费，不存在额外的 20710 → 20711 → 20712 通关串行链。

三关普通目标是 `41028`（ワノクニの雑兵[闇]）。原敌表分别为 14420、14440、14450，杂兵掉落引用分别为 31400、31401、31413。普通小龙、惩罚敌人、实际 Boss 和宝箱不应因为参加战斗就获得杂兵积分。须区分原敌表的槽位命名与客户端最终 `enemy_id=0/99` 的语义，不能仅凭 `boss`／`death` 字段名判断目标。

## 3. 客户端原始计分与解锁链

本次复核沿用原始程序集反编译资料，并用模拟器运行结果交叉验证；静态资料本身不等于运行证据。

|阶段|原客户端行为|服务端对应实现|
|---|---|---|
|入场|保存 `order_quest` 返回的 `enemy_info_list`|[battle_entry.py](../../rtd/services/battle_entry.py)、[battle_layers.py](../../rtd/services/battle_layers.py)|
|击杀|`BattleManager` 依据 Boss／惩罚敌人／坐标定位当前 `EnemyInfo`；原关卡活动 ID 非零时调用 `PlayerData.AddEventPoint(enemyInfo.sp_event_point)`|[battle_generation.py](../../rtd/services/battle_generation.py) 下发每只敌人的积分|
|单局累计|`PlayerData` 单局上限 999|[event_points.py](../../rtd/policies/event_points.py) 冻结本局可上报上限|
|通关|`ComManager.CreateRequest_QuestClear2` 把 `m_GetEventPoint` 放入 `list[].sp_event_point`|[battle_rewards.py](../../rtd/services/battle_rewards.py) 校验及累加|
|结算界面|`MMResult` 在请求完成前会先把所得积分加到本地登录缓存|不能用这一刻的本地余额代替服务器到账证明|
|重登|读取 `login.result.sp_event_point_list`|[accounts.py](../../rtd/services/accounts.py)、[event_points.py](../../rtd/policies/event_points.py)|
|关卡列表|`QuestMenu.Quest` 比较活动余额和 `open_sp_event_point`，设置 `m_SpEventUnlock`|[quest_content.py](../../rtd/policies/quest_content.py) 保留服务端门槛检查|

这一计分路径直接依赖协议字段，没有读取敌人预制体上的“计数标记”。本结论限定于已核实的活动积分路径，不据此声称所有资源标记或模型生命周期问题都不存在。

服务器采用有界的客户端结果申报：上报必须为整数，且位于 0 与冻结上限之间；事件 ID 来自服务端快照，累计上限 99999。协议没有逐只击杀轨迹，不能把可获得积分总量当作已击杀数量，也不能在结算时自动奖励全部可获得积分来掩盖错误。

## 4. 数据与部署证据

### 4.1 原掉落字段确实缺失

只读结构化核查原 `ENEMY_DROP_MASTER`：1808 条记录均没有 `sp_event_point` 字段，模板 id 0 也没有该字段；上述三个杂兵掉落引用没有原始记录。缺失掉落由 [event_reconstruction.py](../../rtd/masters/event_reconstruction.py) 调用 [shingetsu.py](../../rtd/masters/shingetsu.py) 补全。

调查曾怀疑“重建默认生成显式 0，压制缺失回退”。当前数据不支持该猜测：补全器仅按模板现有键构造记录，模板没有该字段，因此实际补全记录也没有生成该字段。不能为解决一个未证实的猜测而删除真实显式 0。

### 4.2 生产与本地审计范围不同

早期本地 runtime revision 34 没有开放历史三关；实际部署为 revision 40，开放三关且 `drops=[]`。早期本地结论不能代替生产结论。最初的生产文件核查显示缺少积分补全模块，且三个调用文件仍为旧实现。部署目录没有 Git 元数据，不能靠仓库提交号证明运行版本，必须比较实际文件及进程行为。

### 4.3 真实配置生成对照

使用真实主表、重建地图和生产运营规则，固定随机种子生成敌人，不改玩家存档：

|关卡|出现的目标杂兵|修复前每只积分|修复后每只积分|其他敌人积分|显式运营积分规则|
|---|---:|---:|---:|---:|---|
|20710|14|0|1|0|无|
|20711|16|0|1|0|无|
|20712|14|0|1|0|无|

这组数量是本次固定生成结果，不是每次开局都保证相同的敌人数量。修复前生成输出的原文件被复用探测路径覆盖，保留的是当时工具输出的明确转录；不能把转录冒充原始捕获。生产源码副本、部署差异和后续客户端响应提供了独立佐证。

## 5. 实际修复边界

最小部署只涉及四个文件：

1. [event_point_recovery.py](../../rtd/policies/event_point_recovery.py)：活动与目标敌人范围明确的缺失补全。
2. [battle_generation.py](../../rtd/services/battle_generation.py)：接收原活动 ID，并按明确优先级生成积分。
3. [battle_entry.py](../../rtd/services/battle_entry.py)：单层生成传入原 `quest.sp_event_id`。
4. [battle_layers.py](../../rtd/services/battle_layers.py)：多层生成传入原 `quest.sp_event_id`。

优先级为：显式运营积分（包括 0）→ 原掉落记录积分（包括 0）→ 缺失补全。未出现敌人和地形对象不计分。100001 仅 41028 每只 1 分；每只 1 分属于本地缺失补全，尚未恢复为官方原始数量。

同一已有策略还限定补全 100000 的亡灵及 100003 的七类海洋敌人，详见策略源码和 [11 月 6 日审计](event-point-open-audit-20261106.md)。本次历史三关实机结果不能扩大为这些活动已全部实机验收。

原主表、属性、等级、掉落概率、开放门槛、运营日程、资源二进制及历史积分没有改写。已开局快照不重算，旧战斗恢复仍可能返回旧的 0 分；新开局才使用新规则。

## 6. 部署中的健康检查问题

API 实际只绑定指定网卡。请求 `127.0.0.1` 失败不能证明生产服务不健康；应从配置、实际进程参数和监听器确认真正的探测地址。

最初短窗口健康检查触发过自动回滚，journal 未见导入崩溃；扩大资源初始化等待窗口后成功部署。最终实际监听地址返回 HTTP 200、`status=ok`、`protocol=RTD-2.4.0`，服务 active/running。只重启 API，没有重启资源服务。备份、文件漂移检查及失败恢复步骤见修复手册。

### 7.1 三轮实际游戏过程

- 默认低等级助战：击杀 3 只目标，积分依次为 1、2、3，随后战败，没有到账。
- 已有高等级助战：累计 13 分，之后战败，没有到账。该结果进一步说明击杀累计正常，但不能当作通关验证。
- 同一高等级助战，使用原生 Cure I：达到门槛后优先前往 Boss，正常击败 Boss、进入 `GameStateGameClear`，本局 7 分。治疗真实扣除 2 魂、恢复 2500 生命。

回放曾在治疗弹窗动画中点击过早而停止。原 `UISkillDialog` 仅在 `m_Status=OPEN` 接受 `ExecSkill`；修正观察就绪断言、正常取消遗留弹窗后从同一 Boss 战继续，未重置战斗或修改存档。
